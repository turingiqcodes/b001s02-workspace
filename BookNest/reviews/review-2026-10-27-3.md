Third pass after the fixes from `review-2026-10-27-2.md`. Most attention went to code changed in that round: the

- The sweep only drops entries whose newest failure is outside the window.
- No reachable route raises a `ForeignKeyViolation` except under a race. Every delete pre-checks the rows that

## 1. Bugs

### [Medium] Starting the updated app before `migrate` breaks every sign-in — `app/main.py:133`, `app/main.py:667` (Confirmed)
**Trigger:** deploy the new code to a DB that only has `001`–`002` and restart without running `migrate`. Every
`POST /api/login` then fails with **500**: `UPDATE … SET last_login_at` raises `UndefinedColumn`. Admin account pages
(`GET/PATCH/DELETE /api/accounts/{id}`) fail the same way via `_account_or_404`. Reproduced on a throwaway DB: 500
before `migrate`, 200 after.
**Why:** the code now depends on migration `003`, and nothing checks the schema at startup. The README tells you to
run `migrate` first, but that's easy to miss in a deploy.
**Fix:** fail fast with a clear message. In `app/main.py`, add a startup hook that checks the column exists, e.g.
`SELECT 1 FROM information_schema.columns WHERE table_name = 'app_user' AND column_name = 'last_login_at'`, and
raise `RuntimeError("Database is behind: run python -m app.manage migrate")` if not. A simpler alternative is to run
`manage.migrate()` on startup, since every migration is idempotent.

### [Low] `create-admin` accepts usernames the sign-in form rejects — `app/manage.py:27`, `app/main.py:58` (Confirmed)
**Trigger:** `python -m app.manage create-admin publisher_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx "…"` (45 characters)
succeeds, but signing in with that username gets **422**. `LoginIn.username` allows at most 41 characters, so the
admin can never sign in. Reproduced on a throwaway DB.
**Why:** the API's username rules (`min_length=3, max_length=40`, `^@?[A-Za-z0-9_.-]+$`) aren't applied in the CLI.
**Fix:** in `create_admin`, check the name against the same regex and length before asking for the password, and
`sys.exit` with the rule if it doesn't match.

## 2. Security

### [Low] 20 or more IPs can still lock one username out — `app/main.py:68` (Confirmed, by design)
**Trigger:** an attacker with 20 addresses (cheap proxies or cloud IPs) sends 5 wrong passwords for `newmoon` from
each, 100 in total. The username-wide limit is then reached, and the real admin gets 429 from anywhere for 15 minutes.
**Why:** the 100-per-username ceiling exists to slow distributed guessing. A hard lock at that ceiling still lets a
well-equipped attacker deny access.
**Fix (optional):** at the username-wide ceiling, don't lock IPs that have signed in successfully as that user before.
Keep a small `last_ok_ips[username]` set, filled on successful sign-in, and skip the `user` limit for those IPs. The
owner then keeps access from known places while new IPs are still slowed.

## 5. Tests & recommendations

### Coverage gaps
- **Startup with an old schema:** nothing checks what happens when the app runs before `migrate` (Bugs #1).
- **CLI input:** `create-admin` has no test, including the username rules (Bugs #2).
- **Collision test is too broad** (`tests/test_api.py`, "002 refuses usernames…"). It catches any `Exception`, so it
  would also pass if `002` failed for an unrelated reason such as a syntax error. Catch
  `psycopg2.errors.UniqueViolation` instead.
- **Distributed lockout:** the username-wide ceiling (100) isn't tested.
- **Frontend under the CSP:** still checked only by the manual Playwright script.
