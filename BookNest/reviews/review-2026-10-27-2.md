## 1. Bugs

### [Low] `prune-keys` erases "last sign-in" for idle users — `app/main.py:671`, `app/manage.py:45` (Confirmed)
**Trigger:** an author signs in on 1 Aug and never again. Their key expires on 1 Aug (or 31 Aug with "Remember me").
`prune-keys` run on 1 Oct deletes it, and their account page now says last sign-in **"never"**.
**Why:** `account()` derives last sign-in from `MAX(api_key.created_at)`, which `prune-keys` now deletes.
**Fix:** add `last_login_at timestamptz` to `app_user` (migration `003`), set it in `login()` together with the key
insert, and read it in `account()`.

### [Low] Delete-vs-insert races still end in a 500 — `app/main.py:217` (`add_my_book`), `app/main.py:1173` (`delete_publisher`) (Plausible)
**Trigger:** the admin deletes publisher 9004, which has no books, while an author adds a book for 9004. Both pre-checks
pass. Whichever commits second hits the real DB's `titles → publishers` foreign key, raising
`ForeignKeyViolation`, which is unhandled. The same can happen with store vs. sale and book vs. sale.
**Why:** the new app-wide handler only maps `UniqueViolation`. The read-only catalog query confirms that the real DB
has these foreign keys.
**Fix:** register the same handler for `psycopg2.errors.ForeignKeyViolation` with a 409 "This changed meanwhile. Reload
and try again."

## 2. Security

### [Medium] Anyone can lock the admin out by guessing wrong 5 times — `app/main.py:61`, `66` (Confirmed)
**Trigger:** an anonymous user sends 5 `POST /api/login` requests for `newmoon` with any wrong password, then repeats
every 15 minutes. The real admin gets **429 even with the right password** for as long as this continues. The test
"5 wrong passwords → … even the right one → 429" shows this behaviour. Usernames are guessable: the admin's is in
the README's setup example.
**Why:** the per-username limit is global, so it can't tell the attacker's failures from the owner's sign-in.
**Fix:** lock the **(username, IP)** pair after 5 failures. Keep the per-IP limit of 20. Replace the global
per-username lock with a much higher ceiling (e.g. 100 per 15 minutes), so a distributed attack is still slowed but
one person can't lock out another:
`LOGIN_MAX_FAILS = {"user_ip": 5, "ip": 20, "user": 100}`, with key `"user_ip:" + username + "|" + ip`.

### [Medium] Behind a proxy that doesn't forward the client IP, every user shares one IP limit — `app/main.py:67` (Plausible)
**Trigger:** the README tells you to run behind a TLS proxy. If nginx proxies to `127.0.0.1:8000` without
`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`, `request.client.host` is `127.0.0.1` for everyone.
After 20 failed sign-ins in total, from any mix of users, **nobody** can sign in for 15 minutes.
**Why:** uvicorn only replaces the client address when the proxy sends `X-Forwarded-For`. It trusts that header from
`127.0.0.1` by default (`FORWARDED_ALLOW_IPS`), so the setup is correct only when the proxy sends it.
**Fix:** document the proxy requirement in the README. Also add a startup warning: if the first request from
`127.0.0.1` lacks `X-Forwarded-For` while `BOOKNEST_BEHIND_PROXY=1` is set, log a warning.

## 3. Performance & efficiency

### [Low] Sign-in failure counts are never swept — `app/main.py:62` (Confirmed)
**Trigger:** failed sign-ins for many different made-up usernames. Each adds a `_login_fails` entry, and an entry is
only pruned when the same username tries again, so these stay until the server restarts. The per-IP limit caps this at
20 new entries per IP per 15 minutes, but a botnet or a long uptime keeps adding to it.
**Fix:** in `_record_fail`, once `len(_login_fails) > 10_000`, drop every key whose newest timestamp is older than
`LOGIN_WINDOW`.

### [Low] `SOLD` aggregates every sale on each use — `app/main.py:37` (Confirmed, carried over)
This is unchanged from the first review and was accepted as negligible at pubs size. Revisit if sales grow into the
tens of thousands.

This is unchanged and was accepted for now. The same note applies as in the first review.
