# BookNest review — 2026-10-27
Scope: all areas (bugs, security, performance, quality, tests) · `app/*.py`, `frontend/app.js`, `frontend/index.html`, `sql/001_booknest_accounts.sql`, `tests/test_api.py`, `README.md`

Method: static scan (`static_checks.sh`), a full read of the backend and the relevant frontend paths, and one read-only
catalog query on the configured DB to list its CHECK constraints. Tests were **not** run: they need an empty throwaway DB.

**What's already solid:** every spec rule in README "Database changes" is enforced in code. All routes except
`/api/login` and `/` require a key with the right role. All SQL takes request values as `%s` parameters (the 5 f-string
queries only insert the `SOLD` constant). Every frontend `innerHTML` value passes through `esc()`/`val()`, and toasts use
`textContent`. Passwords use scrypt with a constant-time compare and a dummy hash for unknown users. API keys are stored
only as hashes and are revoked on logout, password reset and deactivation. The Pydantic field limits match the DB column
sizes and the real DB's CHECK constraints.

## Fix status (updated 2026-10-27)
All findings below are **fixed** except the `APIRouter` split (optional, deferred) and pagination (not needed
at pubs size). Verified against a throwaway Postgres: `tests/test_api.py` now runs **218 checks, all passing**
(192 before, plus 26 new ones for the cases in section 5). Every admin page was also loaded in Firefox under
the new CSP with no console errors.

## 1. Bugs

### [Medium] Duplicate-key races on create return 500 instead of 409 — `app/main.py:710` (and 163, 331, 814, 1011, 1100) (Confirmed)
**Trigger:** the admin double-clicks **Add sale**, or two admins add the same sale line at once. Both requests run
`SELECT 1 FROM sales WHERE stor_id/ord_num/title_id` (line 710), both find nothing, and the second `INSERT` hits the
`(stor_id, ord_num, title_id)` primary key and raises `UniqueViolation`. That error is unhandled, so the request fails with a 500.
The same check-then-insert pattern appears in `add_my_book` (163, auto `title_id`), `create_book` (331),
`create_store` (814), `create_employee` (1011) and `create_publisher` (1100). Two concurrent auto-ID creates compute the
same "next free" ID.
**Why:** the existence check and the insert are separate statements with no lock, and only `create_author`,
`create_account` and `update_account` catch `UniqueViolation`.
**Fix:** add one app-wide handler,
`@app.exception_handler(psycopg2.errors.UniqueViolation)` → `JSONResponse({"detail": "That ID is already used. Reload and try again."}, 409)`.
The pre-checks can stay so the usual case keeps its friendly messages.

### [Low] `create_author` reports every unique violation as "username taken" — `app/main.py:519` (Confirmed)
**Trigger:** two admins create authors at once with the same typed `au_id`. Both pass the line-499 check, and the
second `INSERT INTO authors` raises `UniqueViolation` on the `authors` primary key. The API answers *"That username is
taken."* even when no login was requested.
**Why:** the `except` covers both the `authors` and the `app_user` inserts.
**Fix:** check `e.diag.constraint_name` and pick the message from it, or use the generic 409 handler above.

### [Low] Store list shows an arbitrary discount when a store has several — `app/main.py:769` (Confirmed)
**Trigger:** give store 8042 two discounts (5% and 10%), then open **Stores**. The Discount column shows whichever row
Postgres returns first, and the value can change between loads.
**Why:** `(SELECT d.discount … WHERE d.stor_id = st.stor_id LIMIT 1)` has no `ORDER BY`.
**Fix:** use `MAX(d.discount)` (the best discount), or return a count such as "2 discounts".

### [Low] Sales page counts orders by store *name* — `frontend/app.js:587` (Confirmed)
**Trigger:** two stores with the same name (or both with `NULL` names) each have order `A1`. The Sales page shows 1
order while the Home summary (`main.py:235`, `DISTINCT stor_id, ord_num`) shows 2.
**Fix:** key the set on `r.stor_id` instead of `r.stor_name`.

## 2. Security

### [Medium] No rate limit on `/api/login`, and each attempt costs a full scrypt — `app/main.py:39` (Confirmed)
**Trigger:** a script sends `POST /api/login` in a loop with a known username such as `mgreen`. Nothing slows it down
or locks the account, so passwords can be guessed online. Each attempt also runs scrypt (n=2¹⁴, ~16 MB of memory),
so 40 concurrent attempts tie up every worker thread and about 640 MB of RAM.
**Why:** the README lists this under "Not included yet".
**Fix:** add a per-username and per-IP failure counter (a small `login_attempt` table or an in-memory TTL dict for a
single process). After about 5 failures, answer 429 for 15 minutes. Check the limit **before** running `verify_password`.

### [Low] Usernames are case-sensitive, so look-alike accounts are possible — `app/main.py:42`, `sql/001_booknest_accounts.sql:14` (Confirmed)
**Trigger:** the admin creates `mgreen`, and later `MGreen` for someone else. Both inserts succeed (`text UNIQUE` is
case-sensitive), and an author who signs in as `MGreen` reaches the other account.
**Fix:** store usernames lower-cased (`.lower()` on create, update and login) and add
`CREATE UNIQUE INDEX … ON app_user (lower(username))`.

### [Low] No security headers or CSP — `app/main.py:1146` (Confirmed)
**Trigger:** any page load. Responses have no `Content-Security-Policy`, `X-Frame-Options`/`frame-ancestors` or
`X-Content-Type-Options`, so the app can be framed (clickjacking). If an `esc()` call is ever missed, nothing limits the damage.
**Fix:** in the existing `no_stale_frontend` middleware, add
`Content-Security-Policy: default-src 'self'; frame-ancestors 'none'` and `X-Content-Type-Options: nosniff`.
`index.html` has no inline script, so this CSP won't break it. Check the inline `style=""` attributes in `app.js` and
add `style-src 'self' 'unsafe-inline'`.

### [Low] Password fields have no maximum length — `app/main.py:31`, `472`, `563`, `643` (Confirmed)
**Trigger:** `POST /api/login` with a password of several MB. The body is accepted and scrypt has to process it, which
adds to the cost from the Medium finding above.
**Fix:** add `max_length=128` to `LoginIn.password` and to every password field.

### [Low] TLS to the DB doesn't verify the server — `app/config.py:30` (Confirmed)
**Trigger:** `.env` sets `BOOKNEST_DB_SSLMODE=require` (good), and the DB host is remote. `require` encrypts the
connection but accepts any certificate, so someone on the network path could impersonate the DB. Without `.env`, the
code default is `prefer`, which silently falls back to plaintext.
**Fix:** use `verify-full` with the provider's CA bundle (`sslrootcert`), and change the code default to `require`.

## 3. Performance & efficiency

### [Medium] More than 10 concurrent requests crash with "connection pool exhausted" — `app/db.py:16` (Confirmed)
**Trigger:** 11 or more requests are in flight at once, for example several users or a page firing parallel fetches
(`app.js` uses `Promise.all` in 4 places). FastAPI runs sync routes on a 40-thread pool (anyio `CapacityLimiter(40)`),
but `ThreadedConnectionPool(1, 10)` **raises** `PoolError("connection pool exhausted")` instead of waiting, so the
11th request gets a 500.
**Fix:** either set `maxconn` ≥ the thread limit (e.g. 40, if the DB's `max_connections` allows it), or wrap
`getconn` with a `threading.BoundedSemaphore(10)` so requests queue instead of failing.

### [Medium] Every authenticated request writes to the DB and uses two pool checkouts — `app/auth.py:13` (Confirmed)
**Trigger:** any `GET`, such as opening the Books page. `current_user` runs `UPDATE api_key SET last_used_at = now()`,
then the handler takes a second connection. Read-only page loads turn into writes (row churn, WAL traffic) and double
the pool pressure from the finding above.
**Fix:** only update `last_used_at` when it is stale:
`… SET last_used_at = now() WHERE … AND (last_used_at IS NULL OR last_used_at < now() - interval '5 minutes')`.
This needs a `SELECT` first, or a `RETURNING` on an `UPDATE … FROM` with the condition in a `CASE`. Alternatively,
drop `last_used_at`, since `account()` already uses `MAX(created_at)` as "last sign-in".

### [Low] `SOLD` aggregates the whole `sales` table on every use — `app/main.py:27` (Plausible at larger data sizes)
**Trigger:** `GET /api/me/books` for one author still groups every sale for every title before joining. Postgres can't
push the join condition down into the grouped subquery. This is fine at pubs size (21 sales lines) but grows linearly with sales.
**Fix:** when the volume matters, use a `LATERAL (SELECT SUM(qty) … WHERE title_id = t.title_id)` in the per-author and
per-account queries, plus an index on `sales(title_id)`.

### [Low] `api_key` rows are never purged — `sql/001_booknest_accounts.sql:28` (Confirmed)
**Trigger:** each sign-in inserts a row, and expired or revoked rows stay forever. The table and its `key_hash` index
grow without bound.
**Fix:** add `DELETE FROM api_key WHERE expires_at < now() - interval '30 days' OR revoked_at < now() - interval '30 days'`,
either in a `manage.py prune-keys` command run from cron or on login.

### [Low] List endpoints are unpaginated — `app/main.py:259`, `669`, `855`, `934`, `1052` (Confirmed)
**Trigger:** `GET /api/sales` returns every sales line in one response. That's fine for pubs, but on a real catalog
the response size and render time grow linearly.
**Fix:** when needed, add `limit`/`offset` query parameters (defaults like 200) and paginate in `table()`.

## 4. Code quality

### [Low] The "next free 4-digit ID" SQL is copied verbatim — `app/main.py:804–813` and `1090–1099` (Confirmed)
**Fix:** use one helper, `_next_free_id(cur, table, column)`. Interpolate only the two constant identifiers via
`psycopg2.sql.Identifier`, not f-strings.

### [Low] Repeated small helpers — `app/main.py:494`, `526`, `800`, `826` (Confirmed)
`blank = lambda v: (v or "").strip() or None` is defined four times, and the same expression appears inline about 8
more times. `body.state.upper() if body.state else None` appears 6 times. The "publisher exists or 404" check appears 3 times (160, 198, 298).
**Fix:** add module-level `_blank()`, `_upper()` and `_require(cur, sql, params, msg)` helpers.

### [Low] `main.py` holds every route in 1,166 lines — `app/main.py` (Confirmed)
The `# ---------- … ----------` sections are already good split points.
**Fix:** move each section into an `APIRouter` module (`routes/auth.py`, `books.py`, `authors.py`, `sales.py`, `stores.py`,
`employees.py`, `publishers.py`). This is optional and worth doing before the next big feature.

### [Low] Money is `float` in book models but `Decimal` in discounts — `app/main.py:152`, `285–286` vs `873` (Confirmed)
psycopg2 sends float `repr` values, so `19.99` arrives intact today. Values like `0.1 + 0.2` from a client would be
stored as `0.30000000000000004` rounded to `numeric(19,4)`.
**Fix:** use `Decimal = Field(ge=0, decimal_places=2)` for `price` and `advance`, the same as for `discount`.

### [Low] Small leftovers (Confirmed)
- `requirements.txt` is missing `httpx`, which `fastapi.testclient` needs, so the test script fails on a fresh venv.
- `admin=Depends(require_admin)` is unused in `update_account` (625) and `delete_account` (658). Use `_` as elsewhere.
- `config._load_dotenv` (`config.py:17`) treats `export KEY=…` lines as a key named `"export KEY"`.
- `frontend/app.js:196` always says "Good evening", whatever the time of day.

## 5. Tests & recommendations

### Coverage gaps
`tests/test_api.py` is strong on role rules (every admin mutation is checked with an author key) and on the README
rules. It doesn't cover:
- **Key expiry:** no check sets `expires_at` in the past, and "Remember me" (`remember=True`) is never tested.
- **Admin self-service:** `PATCH /api/me` and `POST /api/me/password` are only checked for the author's 403. The admin
  success path, wrong-current-password (400) and "other sessions revoked" are untested.
- **Account management:** `PATCH /api/accounts/{id}` is only tested for deactivation. Renaming, duplicate username
  (409) and "admin can't be deactivated" (400) are untested. `GET /api/accounts/{id}` is only called once, with no
  assertion on `books` or `last_sign_in`.
- **Publisher delete blocked by employees only:** only the books case is tested.
- **Concurrency/duplicates:** nothing covers the race in Bugs #1.
- **Hostile input:** nothing round-trips `<script>`, quotes or `%`/`_` through titles and names.
- **Schema drift:** `tests/pubs_sample.sql` has none of the real DB's CHECK constraints (e.g. `employee_emp_id_check`,
  `discounts_check`, `authors_zip_check`), so a validation gap would pass tests and fail in production.
- **Runner:** it's a single script with `check()`, not pytest. There's no isolation between steps, no CI, and one
  failure early on skews later checks.

### Prioritized recommendations
1. **Map `UniqueViolation` → 409 in one exception handler.** About 5 lines, and it removes every race-to-500 (Bugs #1, #2).
2. **Fix pool exhaustion.** Raise `maxconn` or put a semaphore around `getconn` (Perf #1). One line to a few lines; it prevents 500s under ordinary load.
3. **Add a login rate limit and password `max_length`** (Security #1, #4). Small and high value before exposing the app beyond localhost.
4. **Throttle the `last_used_at` write** in `current_user` (Perf #2). One SQL change; it removes a write from every read.
5. **Lower-case usernames plus a unique `lower(username)` index** (Security #2). Needs a small migration, `002_…sql`.
6. **Add security headers and a CSP** in the existing middleware (Security #3).
7. **Bring tests up to date:** add `httpx` to `requirements.txt`, copy the real CHECK constraints into `pubs_sample.sql`, add cases 3–12 above, and consider moving to pytest so each area runs isolated in CI.
8. **Cleanups when convenient:** `_next_free_id`/`_blank` helpers, `Decimal` money fields, deterministic store discount, `stor_id` order count, the `APIRouter` split, an `api_key` prune command, `sslmode=verify-full`.
